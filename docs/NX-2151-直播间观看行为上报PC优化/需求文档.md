# PC 直播间观看行为上报优化 — 需求文档

> 工单：PC `NX-2151`（优化 PC 已上线的 `NX-2082`；参照 H5 `NX-2122`）
> 状态：已确认（用户 2026-11-18）；11-19 需求变更：PWA 窗口传 `client_type` 4（D15），**用户 11-19 已确认** · 2026-11-19
> 本文只写「要做成什么样、要注意什么」，不涉及代码。怎么在 PC 代码里实现，见同目录《技术方案.md》（待写）。
> 问题来源：H5 需求目录下的《PC待优化清单-NX-2082.md》（P1～P14）。本单处理哪几条见第十节、第十一节。

## 一、目标

PC 直播间已经上线了观看行为上报（NX-2082），后端据此统计每个直播间的「在看人数」。本单做两件事：

1. **补上续期**：会话过期时（心跳返回 `data: false`），重新上报「进入」、换用新的会话 ID，与 H5 一致；
2. **修正现有实现的问题**：该停的时候停不下来（离开、换场、关播后仍在发心跳），关播的直播间仍被统计，上报失败会打扰用户甚至把用户退出登录。

一句话标准：在网络正常的情况下，用户在直播间停留满 10 秒，页面发出一次「进入」；之后每 3 分钟发出一次「心跳」，会话过期时自动续期；用户离开、换场或关播后，不再发出这一场的任何上报；整个过程用户完全感觉不到。改完后 PC 与 H5 的规则一致，只有客户端类型和页面本身的差异（第六节）。

## 二、接口约定（与 H5 共用，后端已有，本单不改接口）

| 接口 | 用途 | 参数 | 返回 |
|---|---|---|---|
| `api/live_watch_record/enter`（POST） | 上报「进入」 | `anchor_id` 主播 ID；`live_id` 直播记录 ID；`match_id` 比赛 ID；`channel_code` 渠道号；`client_type` 客户端类型 | `watch_session_id` 观看会话 ID |
| `api/live_watch_record/heart`（POST） | 上报「心跳」 | `watchSessionId` 观看会话 ID（驼峰写法） | `data`：`true` 表示会话正常；`false` 表示会话已过期，需要续期（R17） |

参数口径：

- `client_type`：普通浏览器标签页传 **1**（与现在相同）；从安装后的 PWA 窗口打开传 **4**（R18、D15）。H5 传 2。
- `live_id`：直播信息里**原始的**直播记录 ID，**不是聊天室 ID（vid），也不是比赛 ID**。取法沿用已上线的 PC：有 `live_id` 用 `live_id`，没有就用 `id`（D12，两端一致）。
- `channel_code`：与本站其他接口使用的渠道号一致，**不能为空**（为空时后端会拒收）。用户第一次直接打开直播间、地址里没有渠道参数时，也要带上站点的默认渠道号。
- 一次「进入」的所有参数必须属于**同一场直播**，并且在**开始计 10 秒的那一刻**一次确定下来，不能出现 A 场的直播记录 ID 配上 B 场的比赛 ID（修 P7）。

**「一场」的定义**（与 H5 相同）：主播、比赛、直播记录三者都相同，才算同一场；任何一个变了，就是新的一场。比赛 ID 为空的直播间，以主播和直播记录区分。

## 三、规则

「与 H5」一列说明和 H5 `NX-2122` 的规则是否一致；「PC 现在」一列说明本单改了什么（括号里是待优化清单编号）。规则编号与 H5 对齐，方便两端对照。

| 编号 | 规则 | 与 H5 | PC 现在 |
|---|---|---|---|
| R1 | 用户进入直播间、页面拿到这场直播的信息后开始计时，**满 10 秒**上报一次「进入」 | 相同 | 不变 |
| R2 | 10 秒内离开直播间，不上报 | 相同 | 不变 |
| R3 | 「进入」成功并拿到会话 ID 后开始计时，**每 3 分钟**上报一次「心跳」，带上这个会话 ID | 相同 | 不变 |
| R4 | **首次**「进入」失败、超时或没拿到会话 ID：不发心跳，也不重试「进入」，这次观看就不再上报。续期时的「进入」失败不适用本条，按 R17③ | 相同 | 不变 |
| R5 | 心跳某一次失败（接口报错、网络失败、登录失效等）：跳过，下一个 3 分钟照常发，会话 ID 不变。会话是否过期**以心跳返回为准**，过期时按 R17 续期 | 相同 | 失败处理不变；新增续期 |
| R6 | 离开直播间（站内跳到别的页面、关闭页面、刷新页面）：立即停止这一场的所有上报。**「进入」请求已发出但还没返回时离开，返回后也不能再开始心跳**。刷新页面等于离开后重新进入 | 相同 | **改**：现在返回后仍会启动心跳，离开后在其他页面一直发（P1） |
| R7 | 同一个页面里换到另一场（PC 上就是**连播**）：**页面拿到并确认新一场的信息时**，旧一场立即停止，新一场从这时起重新计 10 秒，拿新的会话 ID。旧一场还没返回的「进入」结果作废。收到连播通知到拿到新一场信息之间（约 3 秒），仍算旧的一场。**拿新一场信息失败的，旧一场照常继续上报** | 相同 | **改**：现在一收到连播通知就停，拿新信息失败后不再恢复（P5）；旧一场的「进入」回包会启动旧会话心跳（P2） |
| R8 | **同一场不重复进入**：页面因为任何原因重新获取同一场的信息，只要还是同一场，就不重新计时、不换会话 ID | 相同 | PC 现在只有首次打开和连播两个入口会重新获取，本条防止以后新增入口时出错 |
| R9 | 关播：停止心跳；如果 10 秒还没到，取消这次「进入」；「进入」已发出但还没返回的，返回后也不开始心跳。关播后这一场不再上报 | 相同 | **改**：现在只停心跳，10 秒内关播时仍上报进入，且之后心跳停不下来（P4）；关播后会话 ID 没清（P9） |
| R10 | 打开直播间时，页面判定为已关播：不上报 | 相同 | **改**：现在 10 秒后照常上报进入，心跳一直不停（P3） |
| R11 | 上报对用户**完全无感**：不弹任何提示；后端返回「登录失效」也**不能**让用户被退出登录；不影响播放 | 相同 | **改**：现在上报失败会弹错误提示，返回登录失效会提示并退出登录（P8，已按代码核实） |
| R12 | 回放（页面正常播放回放内容时）、未开播（倒计时中）、游客、分享短链进入的直播间：都照常上报。回放的直播间如果页面判定为已关播，按 R10 不上报 | 相同 | 照常上报不变；已关播的按 R10 |
| R13 | 同一用户开多个标签页：每个标签页各自上报、各自拿会话 ID，互不影响；前端不去重（D7） | 相同 | 不变（P14 不做，见 D7） |
| R14 | 页面切到后台：前端不暂停、不主动补发、不重新进入。回到前台后，如果页面没有重新加载、而且还是同一场，就不重新进入、不换会话 ID；后台期间换了场的，按 R7 处理。回到前台后心跳返回 `false` 的，按 R17 续期（这不算违反本条） | 相同 | 不变（P13 不做） |
| R15 | 离开到站外再点浏览器返回，如果页面从浏览器缓存原样恢复（没有重新加载），不算离开：已有会话的继续用原会话发心跳；还在 10 秒计时中的继续计时；「进入」请求离开前已发出的，恢复后照常处理返回结果。如果浏览器重新加载了页面，按 R6 等于重新进入。从缓存恢复后心跳返回 `false` 的，按 R17 续期 | 相同 | 补齐口径 |
| R16 | 观看过程中登录、退出、切换账号：**登录态变化本身**不触发重新进入，继续用原来的会话 ID。之后如果续期（R17），续期的「进入」用**当时的**登录身份（D10） | 相同 | 不变；续期部分新增 |
| R17 | **续期**：心跳请求成功、且返回的 `data` **严格等于** `false`，说明会话已过期，前端立即续期：①**马上**重新上报一次「进入」，不再等 10 秒；主播、直播记录、比赛、客户端类型用这一场原来的那组，不重新取；渠道号和登录身份与本站其他接口一致，用续期**当时的**值（D10、D11）；②拿到新的会话 ID 后，之后的心跳都改用它，并**从续期成功的时刻重新算 3 分钟**，旧的心跳节奏作废；③续期失败（「进入」报错、超时或没拿到会话 ID）：保留旧会话，下一个 3 分钟照常发心跳，再遇到 `false` 再续期，两次心跳之间不额外重试，一次续期没返回之前不发起第二次；④续期请求还没返回时离开、换场或关播：返回结果作废，不开始新的心跳，也不影响新一场自己的续期；续期成功之后才返回的旧会话心跳结果，一律忽略；⑤续期请求同样对用户无感（R11）。心跳返回 `true`、返回里没有 `data` 字段、或 `data` 是其他值（如字符串 `"false"`、`null`）：按正常处理，不续期 | 相同（H5 R17、D10） | **新增** |
| R18 | **客户端类型**：普通浏览器标签页（包括浏览器全屏、视频全屏）传 1；从安装后的 PWA 窗口打开传 4。判断规则与 PC 在线心跳完全相同，**全项目只用一份判断**：页面在安装后的 PWA 窗口里（独立窗口等显示模式，或 iPad、iPhone 从主屏幕打开）才算 PWA，读取不到时按普通网页。**打开直播间页面时判断一次**，这一页之后的首次进入、换场、续期都用这个值（与在线心跳一样在打开时判断；避免 PWA 窗口里视频全屏时换场被误判成 1） | H5 不能安装成 PWA，固定传 2 | **新增**（D15） |

## 四、场景与预期

| 编号 | 场景 | 预期 | 对应规则 |
|---|---|---|---|
| S1 | 进入直播间，停留 10 秒以上 | 拿到直播信息后约 10 秒一次「进入」；「进入」成功后每约 3 分钟一次「心跳」，会话 ID 不变 | R1、R3 |
| S2 | 进入后 10 秒内站内跳走、关掉标签页或刷新 | 这次不上报（刷新后按新的一次进入重新计时） | R2、R6 |

| S6 | 连播时，页面拿新一场信息失败 | 旧一场照常发心跳（还在 10 秒计时中的继续计时），不中断 | R7 |
| S7 | 收到连播通知，但页面拿到的还是同一场 | 不出现第二次「进入」，会话 ID 不变 | R8 |
| S8 | 观看中主播关播 | 心跳停止；有推荐直播间时页面约 10 秒后整页跳过去，在新直播间重新计时 | R9、R1 |
| S9 | 进入后 10 秒内主播关播 | 不上报「进入」，也没有心跳 | R9 |
| S10 | 「进入」已发出、还没返回时主播关播 | 返回后不开始心跳 | R9 |

| S12 | 上报接口报错、超时，或返回登录失效 | 没有任何提示，不被退出登录，直播正常看 | R4、R5、R11 |
| S13 | 断网 | 「进入」失败就不再上报这一场；心跳失败就跳过。网络恢复后不补发 | R4、R5 |
| S14 | 把直播间标签页切到后台，过一段时间再切回来 | 没有重新进入，会话 ID 不变；后台期间心跳发了几次只记录 | R14 |

| S18 | 手动刷新直播间页面 | 等于离开后重新进入：新的「进入」、新会话 ID | R6、R1 |

| S21 | 观看中，某次心跳返回 `data: false` | 马上一次新的「进入」（参数与这一场原来的一致），拿到新会话 ID；从这时起约 3 分钟一次心跳，带新会话 ID；旧会话 ID 不再出现 | R17 |

| S24 | 切到后台或从浏览器缓存恢复后，回来的第一次心跳就返回 `false` | 按 S21 续期；这次「进入」是续期引起的，不算违反 R14、R15 | R17、R14、R15 |
| S25 | 登录、退出或切换账号后（页面没刷新），心跳返回 `false` | 续期的「进入」带当时的登录身份，拿到新会话 | R17、R16 |
| S26 | 心跳返回 `data: true`、没有 `data`、或 `data` 为其他值 | 不续期，没有额外的「进入」 | R17 |
| S27 | 从安装到桌面的 PWA 窗口打开直播间，停留到续期 | 「进入」和续期的「进入」都带 `client_type` 4 | R18 |
| S28 | 普通标签页按 F11 全屏后打开直播间，或观看中把视频全屏后发生连播 | 「进入」带 `client_type` 1，不被当成 PWA | R18 |
| S29 | 在 PWA 窗口里把视频全屏，期间发生连播 | 新一场的「进入」仍带 `client_type` 4 | R18 |

## 五、特殊说明

1. **PC 页面里只有连播会在同一页面换场。** 在直播间里点推荐主播、关播后跳到推荐直播间、从关注列表进入等，都是整页重新打开，等于离开后重新进入（R6）。技术方案阶段会把所有重新获取直播信息的入口再排查一遍，统一按 R7、R8 处理。
2. **后台标签页**：桌面浏览器的后台标签页一般仍能发出心跳，但浏览器可能降低定时任务的频率（例如后台久了被节流），心跳间隔可能变长。这一版不针对后台做处理（R14），与 H5 一致。
3. **关播后又重新开播**（P6，本单不做）：PC 关播后约 10 秒会整页跳到推荐直播间，跳过去等于重新进入；只有没有可推荐的直播间时页面才会停在关播状态，这时页面本身也不会恢复播放，用户刷新后会正常重新进入。所以这个场景在 PC 上基本不出现，不另做处理。

## 六、与 H5 的行为差异

只列**用户或后端能看到的行为**差异；代码层面的差异见《技术方案》。

| 编号 | 方面 | H5 | PC | 类型 |
|---|---|---|---|---|
| C1 | 客户端类型 | 2（不区分 PWA） | 普通网页 1，PWA 窗口 4 | 有意不同（H5 不能安装成 PWA） |
| C2 | 同一页面换场的入口 | 连播、换主播、播放出错自动重新获取等多个入口 | 只有连播（其他都是整页重新打开） | 页面差异，规则相同 |
| C3 | 关播之后 | 10 秒后自动跳到推荐直播间 | 有推荐直播间时 10 秒后整页跳过去；没有时停在关播状态 | 页面差异，上报规则相同 |
| C4 | 切到后台 | 手机浏览器可能暂停、降频或冻结 | 桌面浏览器一般仍能发出，可能降频 | 平台差异 |

除以上几点，第三节 R1～R17 两端一致。本单改完后，H5 需求文档第六节里 C2～C5（PC 的旧行为）将不再成立。

## 八、验收标准
