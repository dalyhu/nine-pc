## 二、与 H5 的写法差异

行为差异见《需求文档》第六节。下面是代码写法上的差异：

| 编号 | 方面 | H5 | PC | 为什么 |
|---|---|---|---|---|
| I1 | 独立模块 | `utils/liveWatchRecord.js` | `src/utils/liveWatchRecord.js`，结构、状态机、续期要点与 H5 **逐条一致**，只改端差异 | 两端规则相同，状态机照 H5 写最稳；P11 |
| I2 | 请求怎么传入 | 注入 `post(url, body, options)`，状态机统一传 `silentError` | 注入 `enter(data)`、`heart(data)` 两个函数（就是 `api/user.js` 的两个接口函数）；`silentError` 写在 `api/user.js` 里 | PC 所有接口都在 `api/` 里定义；NX-2124 也是在 `api/user.js` 里写 `silentError: true` |
| I3 | 会话 ID、心跳结果的取法 | `$http` 返回解包后的 `data`：`res.watch_session_id`、`res === false` | 请求层返回整包：`res.data.watch_session_id`、`res.data === false` | 照抄 H5 会永远拿不到会话 ID、永远不续期 |
| I4 | 接入点 | `getLiveDetail` 三种 `action` + 播放异常重试 | 两处：`initRoomInfo`（首次和连播）；播放器子组件的播放异常重试查到换场时，把它拿到的原始直播信息随连播事件一起交给 `live.vue` 同步（播放器只改这一行 `$emit`）。重试查到关播会转成关播事件 | PC 入口少（第一节）；重试已经拿到并切到了新一场，不能等父组件 3 秒后再拉一次才同步，那次失败会让上报停在旧一场（Codex 审查 F3） |
| I5 | 关播挂在哪 | `handleLiveClosed()` 开头 | `watch(liveClosed)` 里调 `markClosed()` | PC 所有关播路径都会把 `liveClosed` 改成 `true`（第一节），H5 有一条重试路径不改 `liveClosed` 才不得不挂在函数里 |
| I6 | 连播时何时停旧一场 | 拿到新信息后由状态机判断 | 删掉 `handleMatchInfoToggle` 里的立即清理，同样交给状态机 | 需求 R7、D9（P5） |
| I7 | `silentError` 的来源 | 基于 NX-2123，直接用 | 把 NX-2124 `78917e2a` 对 `request-o.js`、`request.js` 的改动**逐字节**带进本分支（直接取那两个文件） | 用户 11-18 定（Q2 选②）：本单不和 NX-2124 绑定上线；两边内容完全相同，合并时不冲突 |
| I8 | `client_type` | 2 | 普通网页 1、PWA 窗口 4：调用 NX-2124 的 `getPcClientType(window)`（`src/utils/onlineReportUtils.js`，逐字节带入，不另写） | 需求 R18、D15；全项目只有一份 PWA 判断 |
| I9 | 直播信息被改写 | H5 会原地改写 `res.info.id`，必须提前取 | PC 是拷贝后再改，不受影响；仍然在 `.then` 最前面取，保持「取参数在改写之前」 | H5 回归报告 F2 的教训 |

## 五、核心模块 `src/utils/liveWatchRecord.js`

```js
import { getPcClientType } from './onlineReportUtils.js' // 与 PC 在线心跳共用（需求 R18、D15）
export const LIVE_WATCH_ENTER_DELAY = 10 * 1000
export const LIVE_WATCH_HEARTBEAT_INTERVAL = 3 * 60 * 1000

// data 是 getRoomInfo 返回的 res.data（{ userData, info, ... }）
// 返回 { payload: { anchor_id, live_id, match_id, channel_code }, closed }；没有 info 时返回 null
export function pickLiveWatchInfo(data, { fallbackAnchorId, channelCode }) { ... }

// enter(data)、heart(data) 返回 Promise，成功时 resolve 请求层的整包 res
export function createLiveWatchRecord({ enter, heart, getClientType = () => getPcClientType(window), timers = window, logger = console }) {
  let enterTimer = null
  let heartbeatTimer = null
  let sessionId = ''
  let enterData = null     // 这一场开始计时时记下的整组参数（含 client_type）
  let currentKey = ''      // `${anchor_id}|${match_id}|${live_id}`
  let closed = false
  let generation = 0       // 开始、关播、停止都加一，丢弃过期回包
  let renewingGen = null   // 续期令牌：正在续期的那一批的批次号

  return {
    start(payload) { ... },      // 标识相同直接返回；不同则 clearAll() 后重新计时；没有 anchor_id 不开始；match_id 为空照常
    markClosed(payload) { ... }, // clearAll()，closed = true；传了 payload 就以它为当前这一场
    stop() { ... },              // clearAll()，标识置空
    get state() { ... }          // 只给单测用
  }
}

// 直播信息回包的「闸门」：丢弃过期回包；关播时作废所有已发出未同步的请求
export function createLiveInfoGate() {
  let issued = 0   // 已发出的最大序号
  let synced = 0   // 已同步的最大序号
  return {
    issue() { return ++issued },              // 发 getRoomInfo 前取序号；播放器重试的快照到达时也取一个
    accept(seq) { return seq > synced },      // 回包是否还有效
    commit(seq) { synced = seq },             // 确认同步成功后才推进（空信息、解析失败不推进）
    invalidate() { synced = issued }          // 关播：关播前发出的请求全部作废
  }
}
```

`pickLiveWatchInfo` 的取值与已上线代码一致：

- `anchor_id`：`userData.uid` 大于 0 用它，其次 `info.uid` 大于 0，最后 `fallbackAnchorId`（`initRoomInfo` 发请求时的主播 ID）；
- `live_id`：`info.live_id`，为 `null`、未定义、空字符串、`0`、`'0'` 时取 `info.id`，同样的空值规则（与 H5 相同；需求 D12；比已上线的 `??` 多把空字符串和 0 当空值，结果对正常数据不变）；
- `match_id`：`info.match_id`，为空照传；
- `channel_code`：传 `query.channel_code || store.state.channelCode`（与现在相同；请求拦截器发出时会统一覆盖成全局渠道号）；
- `closed`：`info.islive == null || Number(info.islive) === 2`，与页面判断关播的条件相同。

**续期要点**（与 H5 技术方案第五节逐条对应）：

1. 首次进入和续期都用 `enterData`，不重新从页面取；渠道号和身份由请求拦截器在发出时写入，是续期当时的值（需求 D10、D11），状态机不另外冻结。
2. 心跳发出前记下 `gen = generation`、`sid = sessionId`；回包时 `gen !== generation` 或 `sid !== sessionId` 就丢弃（离开、换场、关播后的回包，续期成功后才回来的旧会话心跳）；通过后 `res?.data === false` 才续期，`true`、`null`、没有 `data`、字符串 `'false'` 都按正常处理。
3. 续期：`renewingGen === generation` 时直接返回（这一批已有续期在途）；否则 `renewingGen = generation`，立即调 `enter(enterData)`。回包批次号不符→丢弃；拿到 `res.data.watch_session_id`→清掉旧心跳定时器，用新会话重新启动 3 分钟定时（从此刻算）；失败或没有会话 ID→`console.warn`，旧会话和旧定时器不动。最后只有 `renewingGen` 仍等于这次的批次号时才置回 `null`。
4. `clearAll()` 递增批次号，旧令牌自动失效：新一场可以独立续期，旧续期晚回来也解不了新一场的锁。
5. 续期不改批次号；续期在途时下一次心跳又返回 `false`，因令牌在不会重复续期。

- `initRoomInfo` 里页面自己赋值 `liveClosed` 在 `syncLiveWatch` 之后，触发的 `watch` 再调一次 `markClosed()`，对同一场是重复调用，结果不变。

- 序号只管上报，不改页面原有的数据应用：过期的 `getRoomInfo` 回包照旧改写页面数据，这是原有行为，本单不动（风险 K2）。
- `getRoomInfo` 失败走原来的 `.catch`，只复位 `isDoingMatchInfoToggle`，旧一场照常上报（S6）。
