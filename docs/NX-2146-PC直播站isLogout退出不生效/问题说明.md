# NX-2146 问题说明：PC 直播站带 isLogout=1 打开时退出不生效

> 状态：已确认（2026-11-17）
> 类型：缺陷，低优先级，线上已有。技术方案并在本文件第五～八节。
> 分支：`feat/NX-2146`，起点 `origin/main` `965b7d8f`。
> 排查原始记录在 NX-2142 / NX-2135 的 PRE、BETA 回归报告里（不在本仓库）。

## 一、现象

直播站已登录时，用带 `isLogout=1` 的地址打开直播站（例如 PC 论坛判定已退出后，点「直播大厅」或「返回小九」），页面会调退出接口并自动刷新一次，但刷新后**仍是登录状态**。此时界面上的登录信息对应的 token 已经调过退出接口（`SignOut`），后续需要登录的操作可能失败。

## 二、复现步骤

不需要论坛配合：

1. 在 PC 直播站登录任意账号。
2. 同一浏览器地址栏打开 `https://<环境域名>/?channel_code=AAA&isLogout=1`。
3. 等页面自动刷新一次。

- 预期：刷新后是游客。
- 实际：刷新后仍是登录状态（BETA 稳定复现，PRE 可复现）。

前提：直播站的 token 仍有效。token 已失效时「刷新用户信息」接口失败，不会写回，退出正常。

## 三、根因

页面启动时「刷新用户信息」和「退出」并发执行，前者返回后用内存里的旧登录信息覆盖了后者刚清掉的本地存储。行号以 `origin/main` `965b7d8f` 为准：

1. **先发退出请求**：`src/main.js:45-52` 先 `await store.dispatch('init')`，返回后同步 `app.mount`。`init` 在 `src/store/index.js:457-458` 只是用 `setTimeout` **注册**了 `updateUserInfo`，还没执行。挂载时 `src/App.vue` 的 `onMounted` 调 `setForumUrl()`（第 225 行），`isLogout` 分支（第 91-99 行）在已登录时 `await store.dispatch('logout')`，`SignOut` 请求先发出。
2. **再发刷新用户信息**：当前任务结束后，第 1 步注册的定时器触发 `updateUserInfo`，发出 `Member/info` 请求。两个请求同时在途。
3. **退出只清本地存储，刻意不动 Vuex**：`src/store/index.js:382-404` 的 `logout()` 先调 `logoutService()`，再把 `localStorage.userInfo` 写成 `{}`、删掉 `visitorInfo`。注释说明了原因：commit 会触发 `SET_USERINFO` 里的延迟 reload，并在页面存活期间制造一段空身份窗口，所以靠调用方整页刷新重建状态。于是在 reload 真正生效前，**Vuex 里仍是旧的登录信息**。
4. **刷新用户信息返回后写回**：`src/store/index.js:370-380` 的 `updateUserInfo()` 拿到接口数据后执行 `commit('user/SET_USERINFO', { ...state.user.infoData, ...data })`。`state.user.infoData` 是第 3 步没清的旧登录信息，`SET_USERINFO`（`src/store/modules/user.js:26-40`）在 `id` 存在时把它加密写回 `localStorage.userInfo`；`id` 没变，也不会触发它自己的延迟 reload。
5. 刷新后 `init` 从 `localStorage` 读到被写回的登录信息（`src/store/index.js:442`），用户又「登录」了，用的是已退出的 token。

竞态窗口：`SignOut` 返回后 `logout` 清掉本地存储，`App.vue` 紧接着调 `window.location.reload()`；但 `reload()` 只是开始导航，旧页面的 JS 要到新页面开始加载才停止执行。`info` 的返回落在这段时间里，就会把旧登录信息写回。窗口长短取决于刷新本身多快：BETA 走公网、刷新慢，所以稳定复现。反过来，`info` 回来得太晚（旧页面已卸载），回调不会执行，也就不会复现，所以**只给 `info` 加延迟不能稳定复现**。浏览器内复现记录（控制台先派发 `updateUserInfo` 再派发 `logout`，不刷新）：`localStorage.userInfo` 长度 1536 → `logout` 后 2（`{}`）→ `updateUserInfo` 返回后又是 1536。

**引入提交**（Jerris，2026-08-06，均已在 `main`、线上）：`4806d340`「fix: 退出登录优化」把 `logout` 改成不 commit Vuex；`92e57ad9`「fix: isLogout 退出逻辑也优化下」让 `isLogout` 分支也走这条路。以上由 `git show 4806d340 92e57ad9` 核实。在这之前 `logout` 第一步就 `commit('user/SET_USERINFO', {})` 清 Vuex，此后发出的 `updateUserInfo` 拿不到 `user_id`，不会发请求；已在途的那次合并时以空对象为底，能不能写回取决于 `info` 返回里是否带 `id`，**没有验证**，所以「旧版本一定没有这个问题」只是推断。另外 `92e57ad9` 删掉了 `src/__tests__/store/logout.spec.js`（445 行；`*.spec.js` 不在现在 `npm test` 的匹配范围内）。

**同一根因的其他路径**（推断，未实测）：`updateUserInfo` 共有 16 处派发（含 `init` 那一处）（如导航栏用户菜单弹出时 `LoginBtn.vue:206`、`SpaceAndMine.vue:167`），三处退出入口（`LoginBtn.vue:164` 页内「退出登录」、`personalCenter/mainMenu.vue:57`、`utils/request-o.js:52` 登录失效）都是「`logout` 后整页刷新」。比如打开用户菜单（触发刷新用户信息）后马上点「退出登录」，如果接口恰好在刷新前返回，也会退出不生效。登录失效（code 700）那条路 token 已失效，`info` 会失败，基本不受影响。本单的修法在 `updateUserInfo` 一处挡住写回，这些「`updateUserInfo` 与退出」的竞态一并覆盖。

**修法覆盖不到的同类写回**（全仓 `SET_USERINFO` 共 7 处提交，逐一看过）：

- `src/utils/im/index.js:142`：IM 推送余额变动时，以旧 Vuex 为底写回。`logout` 里的 `IM.destroy()`（第 16-18 行）只是给 worker 发一条消息，没有解绑 `onmessage`，所以已经在队列里的推送仍可能落进窗口。要正好在这几百毫秒里有余额变动才会碰上，比本单更少见。见第四节。
- `src/store/modules/user.js:74、89`：登录、邮箱登录返回后写入。这是用户主动登录，写入本身是对的，不算这类问题。
- `src/App.vue:76`（网址带 `token`、`userId`）和第 86 行（论坛 `fingerprintId`）：同步提交，前者在 `isLogout` 分支之前、随后被退出清掉，后者只写空对象，都不是迟到写回。

## 四、修复范围与不修的部分

**修**：`updateUserInfo` 在接口返回后，先确认本地存储里还是发请求时的那个用户，不是就丢弃这次结果、不写回。

**不修**：

| 项 | 原因 |
|---|---|
| `logout()` 刻意不 commit Vuex 的设计 | 是 08-06 为避免空身份窗口里请求被拒做的优化，保留；本单只挡住它带来的写回 |
| `App.vue` 的 `isLogout` 分支、三处退出入口 | 不用改，修 `updateUserInfo` 一处即可覆盖它们与 `updateUserInfo` 的竞态（见第三节末） |
| PC 论坛何时写 `is_logout` cookie、何时给链接带 `isLogout=1` | 论坛 PHP 侧（Discuz），不在本仓；「论坛 cookie 自行过期时会不会标为已退出」由论坛负责人确认，会则优先级上调 |
| 11-16 PRE「PC 已登录点社区论坛未自动登录」 | 很可能是本竞态造成的状态（直播站用着已退出的 token），但未逐步证实；本单修好后如再出现，另行排查 |
| IM 余额推送的写回（`src/utils/im/index.js:142`，见第三节末） | 极少见；要改就得动 IM 的 worker 生命周期，范围超出本单。另开单的话可在同一处加相同的「本地存储仍是该用户」检查 |
| 请求期间退出、又重新登录**同一账号**（id 前后一样） | 本单只比较 id，这种情况旧 `info` 结果仍会写回。`isLogout` 和页内退出都会整页刷新，在途请求随旧页面一起丢掉，只有「另一个标签页在一次 `info` 往返的时间内退出并重新登录同一账号」才会碰上，实际不可能。要防就得同时比较 token 或给会话加版本号，不值得 |
| 后端 | 不改 |

## 五、方案

### 5.1 改法

在 `updateUserInfo` 的 `await info(...)` 之后、`commit` 之前加一道检查：

```js
const { data } = await info({ user_id })
// 请求期间可能已退出（logout 只清 localStorage、不清 Vuex），或在别的标签页换了账号：
// 本地存储里已不是发请求时的用户，就丢弃这次结果，不能把旧登录信息写回
if (String(getCacheUserInfo().id ?? '') !== String(user_id)) return
commit('user/SET_USERINFO', { ...state.user.infoData, ...data })
```

- 用本地存储判断而不是 Vuex：`logout` 只改本地存储，Vuex 此时还是旧值，看 Vuex 判断不出来。
- 比较时统一转字符串：`App.vue` 从网址取的 `userId` 是字符串，接口登录得到的 `id` 可能是数字。
- 时序：如果 `info` 在 `logoutService` 还没返回时就回来了，本地存储还在，照常写回；随后 `logout` 清掉，结果仍正确。只有在清掉之后回来的才丢弃，正好是出问题的那一段。
- 别的标签页切换了账号的情况：本地存储里的 `id` 变了，同样丢弃；那个标签页的 `storage` 事件本来就会让当前页刷新（`App.vue:105-119`），不会留下错误状态。

### 5.2 备选（不采用）

在 `logout` 开头置一个「正在退出」标记，`updateUserInfo` 看到标记就不写回。也能修，但要多维护一份状态，且挡不住「别的标签页换账号」那种不一致；5.1 不引入新状态，故不采用。

### 5.3 可测性

`src/store/index.js` 依赖 `@/` 别名、IM、接口模块，现有 `node --test` 跑不起来。所以把 `updateUserInfo` 里「请求 → 检查 → 提交」这一小段抽成一个不依赖别名的小函数，放在 `src/store/` 下新文件（写法参照 `src/utils/chunkReload.js` 及其单测）。它的参数是：发请求时的用户 ID、请求接口、读本地存储里的用户 ID、读**返回时**的 Vuex 用户信息（作合并的底）、提交。`store/index.js` 的 action 只剩一层薄包装：在发请求前取 `state.user.infoData.id`，其余几项原样传进去。行为除了新增的检查外不变。

薄包装本身没有单测（`store/index.js` 导入不了）。接线对不对，靠两件事确认：代码审查时逐项核对传参；本地回归第 2 条在浏览器里调**真实的** store action 复现竞态（修复前、修复后各做一次）。
