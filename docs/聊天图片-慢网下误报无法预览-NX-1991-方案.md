# 聊天图片 - 慢网下误报「图片无法预览」 NX-1991 方案

> 文档时间: 2026-09-01
> 分支: `feat/NX-1991`，基线 `prod-x9-pc/26-08/26@13`(`e367d5da`)
> 涉及文件: `src/components/dfImage/index.vue`、`src/store/index.js`
> 前置阅读: `docs/聊天HEIC图片裂图-分析与修复方案.md`(同目录，以下简称「HEIC 文档」)

本文是 HEIC 文档的**增量**。HEIC 文档解决的是「本地 blob 解不了码」，本文解决的是
「地址还没算出来就被判定为失败」。两者复用同一个 `#error` 插槽，但触发原因完全不同。

## 一、现象

网络慢时，聊天记录里的图片先展示「图片无法预览」，而不是加载中。列表图片多时会满屏错误文案，
像是图片全坏了；实际图片是好的，等一会儿能正常显示。**且不会出现 loading 效果。**

用户截图: 自己刚发出、上传进度环还停在 76% 的图，气泡里已经显示了错误文案。

## 二、文案出处

「图片无法预览」不是 element-plus 的内置文案(其中文包 `el.image.error` 是「加载失败」)，
而是 HEIC 文档 §五.3 落地的那个 `#error` 插槽内容，位于
`src/components/chatBox/components/messageItem/index.vue:118-123`
(注意不在 `src/views/chat/` 下，全仓仅此一处定义该文案):

```vue
<template #error>
  <div class="pic-placeholder">
    <IconPicture class="pic-placeholder-icon" />
    <span class="pic-placeholder-text">图片无法预览</span>
  </div>
</template>
```

也就是说: **HEIC 那次改动把「解码失败」的占位做对了，但这个插槽会被非 HEIC 的原因误触发。**
本文修的就是误触发。

## 三、根因

### 3.1 空 src 让 el-image 立即进入错误分支

`dfImage/index.vue` 改动前: `imgSrc` 初值是空串(`:50`)，真实地址在 `onMounted` 里才开始算(`:60`)。
Vue 中子组件 `onMounted` 先于父组件执行，所以 `el-image` 挂载时拿到的 `src` 一定是 `''`。

element-plus 的 `loadImage()`(`es/components/image/src/image2.mjs:73-79`)把 `imageSrc` 设为 `''`，
因为 `'' !== undefined`，模板里 `imageSrc.value !== void 0` 通过，`<img src="">` 被真实渲染，
浏览器立即触发 `error` → `hasLoadError = true`。

**这次 error 每张图必然触发，不是偶发。**

### 3.2 错误态与加载态互斥，且错误优先

`image2.mjs:163-187` 的模板结构:

```js
hasLoadError.value
  ? renderSlot(_ctx.$slots, "error", ...)                       // 错误分支，优先判断
  : (Fragment [ <img>, isLoading.value ? placeholder : null ])  // loading 在 else 里
```

`hasLoadError` 一旦为真，`isLoading` 那一支永远进不去。所以不是「先 loading 再报错」，
而是错误态把 loading 完全遮蔽 —— 这正是「不会有 loading 效果」的原因。

### 3.3 为什么慢网才明显

`el-image` 有恢复机制(`image2.mjs:136-145`): `props.src` 变化时 watcher 会复位 `hasLoadError`。
所以 3.1 的假错误**会自愈**，持续时间 = 从挂载到 `imgSrc` 被赋值的间隔。

| 路径 | 取址方式 | 错误态持续 |
|------|---------|-----------|
| `props.src` | `getURL()` 同步 | ≈ 0，肉眼不可见 |
| `props.picBnc` | `await decryptImg()`: fetch + AES 解密 + base64 | **与网络速度成正比** |

聊天消息带 `pic_bnc`(`chatHelper.ts:226,246`)，走第二条。所以「慢网 → 满屏无法预览」
精确对应加密图路径，本次收益面也主要在加密图。

### 3.4 加剧因素: picBncMap 缓存实际失效

`store/index.js:253-255` 改动前:

```js
setPicBncMap(store, data) {
  store.picBncMap = data      // 整体覆盖，不是合并
}
```

mutation 第二个参数是 payload，这里把整个 map 替换成了 `{[单个key]: value}`。
`state:67` 注释写的「避免相同图片地址重复请求 bnc 解密」实际只存得下一条 ——
滚动聊天记录时同一张加密图被反复 fetch + 解密，慢网下进一步拉长 3.3 的错误态窗口。

## 四、改动

### 4.1 `dfImage/index.vue` — 地址未就绪时不挂载 el-image

新增 `resolved` 标志: `computeImgSrc` 得出结论前不挂载 `el-image`，改渲染一个灰底占位 div。
3.1 那次必然的假 error 由此消失。

保留列车既有行为，全部不动:

- `$slots.error` 守卫 — HEIC 文档 §五.2 明确要求，不守卫会让所有未传插槽的调用方
  (头像等)从「加载失败」变成空白。
- `previewDisabled` prop 与 `preview-src-list` 的空数组逻辑。
- `decryptImg` 失败不入缓存 + 明文回落 + `console.warn`。
- `decryptImg(props.picBnc)` **不加** `getSameOriginURL`(见 §六.1)。

配套三点:

1. **`inheritAttrs: false` + 两个分支各自 `v-bind="$attrs"`**。多根节点下 Vue 不做 attrs
   自动继承，否则 `messageItem:110-116` 传的 `class="pic-info"`(承载 138px 尺寸)
   和 `@contextmenu.prevent` 会被静默丢弃，仅 dev warning，布局会塌。
   **不要**用外层 div 包起来 —— `messageItem` 的 `:deep(> img)` 是直接子选择器，
   多包一层会让 img 变孙节点，选择器失配(见 `messageItem/index.vue:510`)。
2. **generation 令牌**。`computeImgSrc` 含 await，长列表复用时 props 快变会让旧的解密结果
   后到、覆盖新状态。await 回来先比对令牌，不匹配直接丢弃。
3. **退避重试** `[800, 2000]`，仅对 `http(s)` 生效。重试期间把 `resolved` 置回 false
   (回到占位态)，避免把错误插槽当成加载态闪一下；预算耗尽则保持挂载、由 `#error` 兜底。

`.df_image_loading` **不设宽高**: 该分支通过 `$attrs` 继承调用方的尺寸 class，
自设 `width/height: 100%` 会与之同优先级冲突，由源码顺序决定胜负。

### 4.2 `store/index.js` — 缓存合并 + 容量上限

`setPicBncMap` 改为合并写入。同时加 `PIC_BNC_CACHE_MAX = 80` 的 FIFO 上限 ——
值是 base64 全量图片数据，只改合并会让长会话在 Vuex 里躺下几百张 base64，
等于拿内存问题换流量问题。原先那个覆盖 bug 反而在意外地压着内存。

## 五、最终效果

| 场景 | 改动前 | 改动后 |
|------|--------|--------|
| 加密图解密中(慢网主要症状) | 「图片无法预览」 | 灰底占位 |
| 地址就绪，图片请求在飞 | 灰底占位(本就正常) | 灰底占位 |
| 自己刚发的图，上传中 | 「图片无法预览」+ 进度环 | 本地 blob 直显 + 进度环 |
| 网络抖动偶发失败 | 「图片无法预览」 | 退避重试自愈，期间保持占位 |
| HEIC 等本机解不了码 | 「图片无法预览」 | 不变，仍走 `#error`(本就是正确行为) |
| 地址真的加载失败 | 「图片无法预览」 | 重试耗尽 → `#error` |

错误兜底能力完整保留，只是触发条件从「渲染即触发」收紧为「真实地址确实加载失败」。
改完之后该文案出现基本代表图片真有问题，而改动前它出现几乎不代表任何问题。

## 六、订正 HEIC 文档中已过时的两处

### 6.1 §十二 的 `getSameOriginURL` 已被删除

HEIC 文档 §十二 描述新增 `getSameOriginURL` 用于 `picBnc` 分支的同源改写。
该函数在 `1899e080` 加入，但已在 `a1e8a455`(「fix: 图片改为优先展示 pic_bnc字段」)中**刻意删除**，
当前全仓不存在。本次**不重新引入**。

若后续再遇到加密图 fetch 跨域失败，需先确认 `a1e8a455` 删除它的意图，不要照 §十二 直接恢复。

### 6.2 §五.1 担心的「气泡全空白」已被缓解

§五.1 提到 `decryptImg` 失败返回 `''` 会让 `imgSrc` 变空串、气泡全空白。
`a1e8a455` 已加明文回落 + `console.warn`，该失败态现在会退到 `props.src`；
`src` 也没有时才是空串，此时 `.empty` 样式(`:96-102`)把错误文案字号打成 0，仍是空白。
本次未改这条链路。

## 七、验证方法

DevTools Network 调 Slow 3G:

1. **加密图历史列表滚动** — 必须用带 `pic_bnc` 的真实消息。普通 url 图本来就不报错，
   测不出问题也验不出效果，这一项最容易走过场。
2. **自己发图上传中** — 本地 blob 直显 + 进度环，无错误文案。
3. **HEIC 回归** — 仍应显示「图片无法预览」占位。本次不该改变这个行为，
   若它变成了一直转圈，说明 §4.1 的重试误把 blob 判成可重试。
4. **布局回归** — 气泡仍是 138×138，右键菜单被拦截(验 attrs 透传)。
5. **头像等其他调用方** — 未传 `#error` 插槽的调用方行为不变(验 `$slots.error` 守卫未被破坏)。
6. **快速切换会话** — 反复切换制造 props 快变，不应出现卡在占位态的图(验 generation 令牌)。

`picBncMap` 修复的验证: 同一张加密图滚出再滚回，Network 面板不应再次请求 `.bnc`。

## 八、未验证 / 不在本次范围

- 本次改动**未做浏览器实跑验证**。`npm run build` 在本机固定以 exit 127 结束于混淆阶段
  (`vite-plugin-bundle-obfuscator` 依赖的命令缺失)，已用 baseline 对比确认与本改动无关;
  Vue SFC 编译与 chunk 生成均通过，eslint 对两个改动文件零报错。§七 需人工过一遍。
- `messageItem/index.vue:154-158` 的刷新按钮 `v-if` 只判断 `chatType !== PUBLIC &&
  !showImageUploadOverlay`，与图片是否真的失败无关，导致私聊每张图旁边都常驻一个刷新图标，
  强化「图片坏了」的观感。属于加剧因素而非根因，本次未动。
- HEIC 转码(上传层转 JPEG)**不做**。HEIC 文档 §三 已定「不转码」原则，
  改走 WS 回包的 `.webp` 字段回显，比转码更省。此处仅作记录，避免后续重复提议。
