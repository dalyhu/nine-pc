# 需求文档：浏览器兼容与白屏兜底

> 状态：第三稿，主要决策已定（待补工单号）　｜　日期：2026-11-10　｜　涉及项目：PC 站（`pc-main`）
> 本文只写「要做什么、做到什么程度算完」，不写技术方案。技术方案在本文 review 通过后另出。

---

## 一、背景

一位用户用 Mac 自带的 Safari 13.1（2020 年发布）打开 PC 站首页，看到白屏。

- **直接原因**：`feat/NX-2031`（PWA）引入的 PWA 库用了 `Object.hasOwn`，这个方法 Safari 15.4 才支持。页面启动时这里报错，应用没有挂载，所以白屏。
- **根本原因**：项目没有明确最低支持哪些浏览器版本，构建没有做降级，新功能上线前也没有检查旧浏览器能不能用。
- **体验问题**：页面不管出了什么问题，用户看到的都是白屏，既没有提示，也没有反馈渠道。

## 二、目标与不做的事

**目标**

1. 支持范围内的浏览器都能正常打开、正常使用网站。
2. 任何情况下都不让用户看到白屏：浏览器版本太低给升级提示，页面出错给错误页。
3. 以后开发新功能，不再因为 JS 语法或浏览器 API 不兼容而白屏。不管代码是人写的还是 AI 写的，都由规范和构建检测来兜住。
4. 版本偏旧、但还在支持范围内的用户，温和地引导他们升级浏览器。

**不做**

- 不兼容支持范围以下的浏览器，这些浏览器只给升级提示。
- **这次不改 CSS**（见 R6）。
- 不做错误上报（见第四节 D7）。
- 不保证所有新功能在旧浏览器上体验一样。核心功能（浏览页面、看直播）必须能用。

## 三、浏览器支持范围（已确定）

| 浏览器 | 最低版本 | 发布时间 |
|---|---|---|
| Chrome | 80 | 2020-02 |
| Edge | 80 | 2020-02 |
| Firefox | 74 | 2020-03 |
| Mac Safari | 13.1 | 2020-03 |
| iOS Safari | 13.4 | 2020-03 |

这组版本只在一个地方配置：仓库根目录的 `browser-support.json`（2026-11-11 由 `vite.config.ts` 的 `MIN_BROWSERS` 迁移过来，见技术方案 C1）。构建配置、兜底页上显示的最低版本、兼容检测都从这里读。

## 五、需求清单

优先级：**P0** 必须做；**P1** 紧接着做；**P2** 排期做。

### 分支 1：`feat/NX-2031`（已实现，待提交）

#### R1　PWA 安全上线的必要修复　P0

- **降级构建**：产物在支持范围内的浏览器上都能运行，语法转换和 JS 内置方法补齐都在构建时自动完成。
- **Service Worker 判断**：浏览器不支持 Service Worker 时（HTTP 访问、部分隐私模式或内嵌浏览器），跳过 PWA，页面照常运行。

**验收**：模拟 Safari 13.1，首页和直播间都能打开；线上和 pre 的接口全部返回 200；Service Worker 正常激活。

#### R2　低版本浏览器兜底页　P0

- **版本过低**：低于支持范围的浏览器，展示「请升级浏览器」，不白屏，也不请求接口、不连 IM。
- **启动失败**：入口文件加载失败、加载卡住、挂载前报错时，展示「页面加载失败」。如果之后应用渲染出来了，这个页面自动消失。

**验收**：已验证的 7 个场景（见验证记录 v3）。

### 分支 2：`feat/browser-compat-guard`

#### R4　页面运行中出错的兜底　P0

现在的情况：应用启动之后如果报错，页面会空掉一块，或者点了没反应。原因是 `main.js` 的 `errorHandler` 和 `router.onError` 只打日志，项目里也没有组件级的错误边界。

要求：
- **页面渲染报错**：只把出错的页面主体替换成错误页（提供刷新和复制诊断信息），顶部导航保留。
- **发版后旧页面跳转失败**：页面分包加载失败时，自动刷新恢复一次；还是失败就展示错误页，不能出现点了没反应。
- **点击等交互里的报错**：不打断页面，在控制台留下记录。
- **404 页**：把「管理员说你不能进去这个页面...」改成面向用户的文案。
- **错误页视觉**：沿用兜底页的风格。

**验收**：
- 人为让某个页面组件报错，看到的是错误页而不是空白，导航还能用。
- 模拟发版后分包返回 404，页面能自动恢复，或者展示错误页。

#### R6　存量 CSS 兼容　本次不做（D8），记为已知限制

Safari 13.1 不支持下面这些写法。页面能正常打开，但样式会有偏差：

| 写法 | 处数 | 在 Safari 13.1 上的表现 |
|---|---|---|
| flex 布局的 `gap` | 约 120（源码） | 间距消失 |
| `:where()` | 3（产物） | 这条样式整条失效 |
| `100dvh` | 2（产物） | 高度失效 |
| `backdrop-filter` 缺 `-webkit-` 前缀 | 3（产物） | 没有毛玻璃效果 |

以后如果要处理，单独立项，并配套做样式回归。

#### R7　开发规范与 CLAUDE.md　P1

- 规范写清楚三件事：哪些会自动处理（语法、JS 内置方法），哪些要人工把关（浏览器 API），哪些浏览器 API 禁用或者用之前要先判断支持情况。
- 在 PC 仓库根目录建 `CLAUDE.md`，不超过 200 行，提交入库，团队共用。大纲包括：
  - 项目概况；
  - 常用命令和本地调试方式；
  - 浏览器兼容规则；
  - 不能动的地方：plugin-legacy 锁定版本、index.html 不能写内联样式、`*-o.js` 加密文件、`store/c`、PWA 必须保持可选；
  - 错误处理约定；
  - 编码约定；
  - 提交前自查；
  - 文档索引。

#### R8　兼容检测工具链　P1

**AI 会不会忘规则？会。** CLAUDE.md 只负责「告诉它」，对话一长规则就会被挤掉。所以真正的拦截要放在构建里：CI 的 Docker 构建会执行 `pnpm run build`，构建不过就发不了版，人和 AI 都绕不过去。

**现状评估**（2026-11-10 实测）：

| 项 | 现状 |
|---|---|
| 语法降级 | ✅ 构建自动处理 |
| JS 内置方法补齐 | ✅ 构建自动处理，第三方库里的也一起补 |
| 浏览器 API 检测 | ❌ 没有 |
| 产物语法检查 | ❌ 没有。验证时写过一个原型脚本 |
| ESLint | 有（8.49），但存量有 139 个错误、284 个警告，CI 也不跑。指望 lint 拦截靠不住 |
| 提交前检查（husky） | 没有 |
| CI | 只跑构建 |

**有一个漏网点**：正则的新语法（比如后行断言 `(?<=…)`）构建时转换不了，会原样留在产物里。旧浏览器解析时报错，整个文件加载失败，又会白屏。所以产物检查是必须的。

**工具评估与建议**：

| 工具 | 拦什么 | 结论 | 理由 |
|---|---|---|---|
| 产物语法检查脚本（自写，基于 `acorn`，项目里已有 8.x） | 产物里超出支持范围的语法，第三方库也查 | **要做，接进 build** | 只认最终产物，最可靠；不用装新插件 |
| `eslint-plugin-compat@6.2.1` | 我们源码里超出支持范围的浏览器 API | **建议装** | 7.x 要求 ESLint 9 和 Node 22，项目是 ESLint 8，所以只能用 6.2.1。另外要单独跑这一条规则，不能混进 `pnpm lint`，否则会淹没在存量错误里。是否接进 build 等技术方案阶段实测存量数量后再定 |
| stylelint 兼容检查 | CSS | 这次不装 | 这次不改 CSS（D8） |
| husky / lint-staged | 提交前拦截 | 不装 | 构建已经是硬卡点，不用再加一层 |

补充：项目用的 caniuse 浏览器数据是 2025-12 的版本（`1.0.30001761`），需要顺手更新，否则升级提示条的阈值和 API 检测会按旧数据判断。2026-11-11 已更新到 `1.0.30001823`（T6a）。（更正：早先写的「2025 年初」读的是本机用户目录下的另一份数据，不是项目的）

**验收**：
- 故意写一个超出支持范围的语法（比如正则后行断言），构建失败。
- 故意写一个超出支持范围的浏览器 API（比如 `BroadcastChannel`），检测报出来。

#### R9　真机验证　P1

- 在真实的 Safari 13.1 上验证首页、直播间、登录和兜底页。之前都是模拟验证。
- 顺便看一下 R6 那几处 CSS 偏差有多严重，作为以后要不要立项的依据。
- 整理一份发版前的兼容测试清单。

#### R10　其他排查　P2

- **H5 项目**：排查有没有同样的 PWA 白屏风险。
- **`sw.js`**：用了 `Object.hasOwn`。旧 Safari 上离线能力不可用，页面本身不受影响。
- **混淆插件**：保持关闭，不开启（2026-11-11 定）。产物不再经过混淆，兼容性验证的结果就能一直有效。

#### R11　软性升级提示条　P1

**目的**：有些用户的浏览器在支持范围内，能用网站，但版本偏旧，部分新特性用不了。不强制，温和地引导他们升级。

**行为**（按你的设想）：

- **开关**：前端环境变量，打开才显示（Q3）。
- **出现与消失**：每次打开或刷新页面都显示在底部居中，8 秒后自动消失。
  - 带关闭按钮。用户主动点 × 关闭后，7 天内不再显示（Q4）。
  - 不挤压、不遮挡页面主要内容。
- **点击**：点提示条跳到浏览器下载页，Chrome 推荐。
- **只针对四大浏览器**：Chrome、Edge、Firefox、Safari。
  - 内嵌浏览器（微信等）不显示，这类用户自己升级不了。
  - 国产套壳浏览器（360、QQ 等）也不显示。
- **和兜底页互斥**：已经显示升级兜底页的浏览器，不再显示提示条。

**什么版本算「偏旧」**（建议）：

| 浏览器 | 发版节奏 | 建议阈值 | 大约落后多久 |
|---|---|---|---|
| Chrome、Edge、Firefox | 约 4 周一版，默认自动更新 | 低于「最新版往前数 4 个版本」 | 约 4 个月 |
| Safari | 每年一个大版本，跟着 macOS / iOS 升级 | 低于「最近 2 个大版本」 | 约 1～2 年 |

- **阈值跟着最新版走**：用「最新版往前数 N 个」来表示，不写死具体版本号。最新版的数据需要定期更新，具体机制在技术方案里定。
- **Safari 用户怎么升级**：Safari 用户升级 Safari 往往要先升级系统，所以文案同时推荐换用 Chrome。

**视觉**（视觉稿：`x9-统筹/升级提示条视觉稿/`，已嵌在线上首页截图）：

- 不用通栏黄条这类旧式警告条，也不引用 browser-update.org 的脚本或样式，按站点风格自己做。
- 浮层样式贴合站点：深色半透明底加毛玻璃，主题色 #d02d54 渐变按钮和图标，大圆角，柔和投影。
- 底部有一条细进度条，提示几秒后会自动消失。
- **位置：屏幕底部居中，距底边 24px**（2026-11-10 定）。放顶部会挡住导航菜单和比赛标题。实测底部居中不挡播放器和聊天输入框（1440×900、1366×768 两种尺寸），不挡右侧悬浮按钮，也不和右下角的 PWA 更新提示重叠。
- 形态：胶囊卡片，一行读完，醒目，适合「几秒后消失、希望用户点」的场景。
- 提示条展示给的就是旧浏览器，所以它自己只能用 Safari 13.1 起就支持的 CSS：不用 flex `gap`、`inset`、`:where()`，毛玻璃带 `-webkit-` 前缀。

**文案方向**（柔和、有引导性，以下是草稿）：

- 「您的浏览器版本稍旧，升级到最新版，观看更流畅、功能更完整。立即升级 ›」
- 「升级浏览器，解锁更好的观看体验 ›　推荐使用谷歌浏览器」

**业内参考**：

- **browser-update.org**：使用最广的第三方升级提示脚本。
  - 阈值可以写具体版本，也可以写「比最新版落后几个」，示例是 `c:-5`，表示 Chrome 比最新版落后 5 个版本就提示。
  - 默认显示在顶部，示例配置是：24 小时后再次出现；用户主动关闭后，150 小时后再出现。
- **GitHub**：
  - 推荐使用 Chrome、Edge、Firefox、Safari 的最新版本，并提示旧版本上「部分功能可能无法正常工作」。
  - 能不能用，靠的是功能检测（`isSupported()`），而不是看版本号。
- **和你的设想对比**：业内常见做法是关闭后隔一段时间再出现；你的设想是每次刷新都出现、几秒后自动消失。你的方式不需要记录用户的关闭状态，更轻量，但提醒频率更高。两种都可以，见 Q4。

**验收**：
- 开关关闭时，任何浏览器都不显示提示条。
- 开关打开时，用低于阈值的 Chrome UA 访问会显示提示条，8 秒后自动消失；用最新版访问则不显示。
- 点 × 关闭后刷新页面，7 天内不再显示；不点 × 只等它自动消失，下次刷新仍然显示。
- 低于支持范围的浏览器只显示兜底页，不显示提示条。
