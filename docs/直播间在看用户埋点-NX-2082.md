# 直播间在看用户数据埋点

> 关联需求：NX-2082  
> 所属分支：feat/NX-2082  
> 实现位置：`src/views/anchor/live.vue`

---

## 一、需求背景

在用户观看直播时，需要上报观看行为数据，用于统计直播间在看用户数。通过进入埋点和心跳埋点两个接口，实现对用户观看行为的持续追踪。

---

## 二、核心功能

### 2.1 进入直播间埋点

**接口：** `enterLiveWatchRecord`

**触发时机：** 用户进入直播间，`getRoomInfo` 接口成功返回后，**延迟 10 秒**调用

**上报参数：**

```javascript
{
  anchor_id: query.value.uid,                                    // 主播ID
  live_id: currentRoomVID.value,                                 // 直播ID (vid)
  match_id: liveBroadcastRoomDetails.value.match_id,             // 比赛ID
  channel_code: query.value.channel_code || store.state.channelCode,  // 渠道码
  client_type: 1                                                 // 客户端类型（PC端固定为1）
}
```

**返回值：** `watch_session_id` - 用于后续心跳上报

---

### 2.2 观看心跳埋点

**接口：** `heartLiveWatchRecord`

**触发时机：** 进入接口调用成功后启动，**每 3 分钟**调用一次

**上报参数：**

```javascript
{
  watchSessionId: '...'  // 从进入接口返回值获取
}
```

**用途：** 持续判断用户是否在线观看

---

## 三、实现方案

### 3.1 调用时序

```
用户进入 /live 页面
  ↓
onMounted() → initRoomInfo('init')
  ↓
getRoomInfo() 接口调用
  ↓
[成功] .then() 回调
  ↓
延迟 10 秒（setTimeout）
  ↓
调用 enterLiveWatchRecord()
  ↓
[成功] .then(res)
  ↓
获取 res.data.watch_session_id
  ↓
启动定时器：setInterval(3分钟)
  ↓
循环调用 heartLiveWatchRecord(watchSessionId)
```

---

### 3.2 为什么从 getRoomInfo 成功后开始计时

进入接口需要的参数（`anchor_id`、`live_id`、`match_id`）都来自 `getRoomInfo` 的返回值。如果从页面加载开始计时，可能出现 10 秒后房间信息还未获取成功的情况，导致参数不完整。

---

### 3.3 为什么是 10 秒延迟

业务设计：过滤"秒进秒出"的用户，只统计真正停留观看的用户。用户在 10 秒内离开页面，进入接口不会触发，不会被计入统计。

---

## 四、清理机制

### 4.1 需要管理的资源

| 资源 | 类型 | 用途 |
|---|---|---|
| `enterWatchTimeout` | `setTimeout` ID | 进入接口 10 秒延迟定时器 |
| `liveWatchHeartbeatTimer` | `setInterval` ID | 心跳 3 分钟定时器 |
| `liveWatchSessionId` | `string` | 会话 ID，用于心跳上报 |

---

### 4.2 清理时机

#### 场景 A：组件卸载（用户离开直播间页面）

**触发：** `onBeforeUnmount()` 生命周期钩子

**清理内容：**
- 清除 10 秒延迟定时器（如果还未触发）
- 清除心跳定时器
- 重置 `liveWatchSessionId` 为空字符串

---

#### 场景 B：连播切换（同页面切换到新直播间）

**触发：** `handleMatchInfoToggle()` 中 `match_id` 变化时

**时机：** 在调用 `initRoomInfo('toggle')` 之前清理

**清理内容：** 同场景 A

**清理后：** 新的 `getRoomInfo` 成功会重新开始埋点流程，产生新的 `watchSessionId` 并启动新的心跳

**为什么需要：** 连播场景下，用户从直播间 A 切换到直播间 B，组件不卸载。如果不清理，心跳会继续上报旧的 `watchSessionId`，导致统计数据错误（直播间 A 的观看时长被错误累计）。

---

#### 场景 C：直播关闭

**触发：** 监听 `liveClosed` 变化为 `true`

**处理：** 清除心跳定时器，停止上报

**原因：** 直播已关闭，用户虽然停留在页面，但不应继续统计为"在看用户"

---

### 4.3 清理函数设计

```javascript
const clearLiveWatchTracking = () => {
  // 清除进入接口延迟定时器
  if (enterWatchTimeout) {
    window.clearTimeout(enterWatchTimeout)
    enterWatchTimeout = null
  }
  // 清除心跳定时器
  if (liveWatchHeartbeatTimer) {
    window.clearInterval(liveWatchHeartbeatTimer)
    liveWatchHeartbeatTimer = null
  }
  // 重置会话ID
  liveWatchSessionId = ''
}
```

统一清理函数，在所有需要清理的场景中调用，避免遗漏。

---

## 五、异常处理

### 5.1 进入接口失败

**处理方式：** 不启动心跳定时器，静默处理（可打印日志）

**原因：** 没有 `watchSessionId`，无法调用心跳接口

**影响：** 不影响用户正常观看直播

---

### 5.2 心跳接口失败

**处理方式：** 单次失败静默跳过，等待下一个 3 分钟周期

**可选优化：** 记录连续失败次数，连续失败 3 次后停止定时器，避免无效请求

---

### 5.3 快速离开（< 10 秒）

**现象：** 用户在 10 秒内离开，进入接口未触发

**处理方式：** 组件卸载时清除 10 秒延迟定时器，不上报

**合理性：** "秒进秒出"用户被自然过滤，符合 10 秒延迟的设计意图

---

### 5.4 定时器重复创建问题（重要）

**问题描述：** 

如果 `initRoomInfo` 在首次调用后的 10 秒内被再次调用，会出现定时器重复创建的问题：

1. 第一次 `getRoomInfo` 成功，创建**定时器A**（10秒倒计时），`enterWatchTimeout` 保存定时器A的ID
2. 在10秒倒计时期间，`initRoomInfo` 再次被调用
3. 第二次 `getRoomInfo` 成功，创建**定时器B**（新的10秒倒计时），`enterWatchTimeout` 被**覆盖**为定时器B的ID
4. **定时器A的ID丢失**，无法被清理，但定时器A仍在后台运行
5. 定时器A会在它原本的时间点触发（可能只剩几秒），导致"没到10秒就发起了请求"

**触发场景：**

- 快速连播切换（虽然 `handleMatchInfoToggle` 中会先调用 `clearLiveWatchTracking()`，但存在异步时序问题）
- 路由参数变化触发重新初始化
- 某些边界情况下的异步回调重入

**问题根因：**

`live.vue` 第 321 行直接赋值创建定时器，**没有先清理旧的定时器**：

```javascript
// ❌ 错误：直接覆盖，旧定时器丢失引用但仍在运行
enterWatchTimeout = window.setTimeout(() => {
  // ...
}, 10 * 1000)
```

**解决方案：**

在创建新定时器前，先清理旧的定时器：

```javascript
// ✅ 正确：先清理旧定时器，再创建新定时器
if (enterWatchTimeout) {
  window.clearTimeout(enterWatchTimeout)
  enterWatchTimeout = null
}

enterWatchTimeout = window.setTimeout(() => {
  // ...
}, 10 * 1000)
```

**修改位置：** `live.vue` 第 320-340 行，在 `getRoomInfo().then()` 回调中

**效果：**

- 确保同一时间只有一个进入接口定时器在运行
- 防止旧定时器的"幽灵触发"
- 每次 `getRoomInfo` 成功后，重新开始完整的 10 秒倒计时

## 六、边界场景处理

### 6.1 回放场景

**标识：** `liveBroadcastRoomDetails.value.isRecord` 或 `store.state.house.isReplay`

**当前方案：** 暂不特殊处理，回放也按直播逻辑上报

**后续调整：** 如果产品确认回放不需要统计，在启动埋点前判断：

```javascript
if (liveBroadcastRoomDetails.value.isRecord) return // 回放场景不上报
```

---

### 6.2 多窗口/多 Tab

**当前方案：** 暂不处理，每个 tab 独立上报

**说明：**
- 每个 tab 会产生独立的 `watchSessionId`
- 后端可根据 `user_id` + 时间维度去重统计真实用户数
- 如果后续需要前端去重，可以使用 `localStorage` + `BroadcastChannel` 实现"主 tab"机制

---

### 6.3 页面可见性（Visibility）

**当前方案：** 暂不处理

**参考：** 代码 518-532 行的 `handlePageVisible` 已被注释，保持一致性

**后续调整：** 如果需要更精准统计"真正在观看的用户"，可以添加 `document.visibilityState` 判断：
- 页面隐藏时暂停心跳
- 页面重新可见时恢复心跳

```javascript
// 记录进入直播间接口
// 接口描述：用户点击客户端，进入直播间后，（10秒后）调用该接口
export function enterLiveWatchRecord(data) {

// 直播间观看心跳接口

export function heartLiveWatchRecord(data) {
  return request({
    url: 'api/live_watch_record/heart',
    method: 'post',
    data
  })
}
```

### 7.2 直播间页面埋点逻辑

**文件：** `src/views/anchor/live.vue`

#### 新增变量

```javascript
let enterWatchTimeout = null          // 进入接口延迟定时器ID
let liveWatchHeartbeatTimer = null    // 心跳定时器ID
let liveWatchSessionId = ''           // 会话ID
```

#### 新增函数

| 函数名 | 说明 |
|---|---|
| `startLiveWatchHeartbeat(watchSessionId)` | 启动心跳定时器 |
| `clearLiveWatchTracking()` | 清理所有埋点相关资源 |

#### 修改位置

| 位置 | 改动 |
|---|---|
| `initRoomInfo()` 的 `.then()` 回调 | ⚠️ **在创建定时器前先清理旧定时器**，然后添加 10 秒延迟调用进入接口 |
| `handleMatchInfoToggle()` | 切换前调用 `clearLiveWatchTracking()` |
| `onBeforeUnmount()` | 添加 `clearLiveWatchTracking()` |

**重要说明：** `initRoomInfo()` 中必须在创建新定时器前先清理旧定时器，防止重复创建导致的"幽灵触发"问题（详见 5.4 节）

#### 新增 watch

监听 `liveClosed` 变化，直播关闭时停止心跳：

```javascript
watch(() => liveClosed.value, (newVal) => {
  if (newVal && liveWatchHeartbeatTimer) {
    window.clearInterval(liveWatchHeartbeatTimer)
    liveWatchHeartbeatTimer = null
  }
})
```

## 十一、测试要点

### 11.1 正常流程

1. 进入直播间 → 等待 10 秒 → 控制台/Network 看到进入接口调用
2. 进入接口成功 → 等待 3 分钟 → 看到第一次心跳调用
3. 继续等待 3 分钟 → 看到第二次心跳调用

---

### 11.2 快速离开

1. 进入直播间 → 5 秒内关闭页面
2. **预期：** 进入接口未调用（10 秒延迟未到）

---

### 11.3 连播切换

1. 进入直播间 A → 等待 10 秒 → 进入接口调用成功
2. 等待 3 分钟 → 第一次心跳调用成功（上报直播间 A 的 sessionId）
3. 点击连播切换到直播间 B
4. **预期：** 
   - 旧的心跳定时器被清理
   - 等待 10 秒后，进入接口再次调用（上报直播间 B 的参数）
   - 获得新的 sessionId，后续心跳上报新的 sessionId

---

### 11.4 接口失败

1. 模拟进入接口失败（Network 限流或返回错误）
2. **预期：** 心跳定时器不启动，不影响直播正常观看

---

### 11.5 定时器重复创建防御（重要）

**测试场景：** 验证在 10 秒倒计时期间重新初始化不会导致提前触发

**步骤：**
1. 进入直播间 A，开始 10 秒倒计时
2. 等待 5 秒后，手动触发路由参数变化或其他可能导致 `initRoomInfo` 重新调用的操作
3. 继续观察

**预期结果：**
- 第一个 10 秒定时器被清理，不会在原定时间点触发
- 从第二次调用开始，重新计时 10 秒
- 只有一次进入接口调用，发生在第二次 `getRoomInfo` 成功后的 10 秒

**验证方法：**
- Network 面板中只看到一次 `api/live_watch_record/enter` 调用
- 调用时间戳应该是第二次初始化后的 10 秒，而非第一次初始化后的 10 秒

---

### 11.6 快速连播切换（10秒内）

**测试场景：** 验证在首次进入后 10 秒内快速切换直播间

**步骤：**
1. 进入直播间 A
2. 等待 5 秒后，点击连播切换到直播间 B
3. 等待 10 秒观察

**预期结果：**
- 直播间 A 的 10 秒定时器被清理，不会触发
- 直播间 B 开始新的 10 秒倒计时
- 只有一次进入接口调用，参数是直播间 B 的信息（`anchor_id`、`live_id`、`match_id` 都是 B 的）

---

### 11.7 直播关闭

1. 进入直播间 → 等待 10 秒 → 进入接口成功 → 心跳启动
2. 主播关闭直播（`liveClosed.value = true`）
3. **预期：** 心跳定时器被清理，不再发送心跳请求

## 十三、后续优化方向

1. **连续心跳失败处理**：记录失败次数，连续失败 3 次后停止定时器
2. **多 tab 主从控制**：使用 `localStorage` + `BroadcastChannel` 实现主 tab 机制，避免重复上报
3. **页面可见性控制**：页面隐藏时暂停心跳，提升统计精准度
4. **回放场景差异化**：如果产品需要区分直播和回放，添加 `isRecord` 判断
5. **埋点数据监控**：添加埋点调用成功率、失败原因的监控上报
