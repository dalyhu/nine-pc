### 为什么这么改

1. **为什么放在 `api/home.js`**：仓库里所有聊天相关接口都集中在这里，保持一处集中。
2. **为什么 URL 加 `api/` 前缀**：Vite 只代理 `/api/`、`/bbs/`、`/upload/`（`vite.config.ts:184-198`）。后端方案里的 `/chatAi/category/list` 是后端路由，前端调用必须补 `api/` 才能走到代理。
3. **为什么用 GET 无参**：后端方案约定该接口 GET、无入参、一次性返回全量。
4. **为什么不做点击埋点**：后端方案里 `use_count` 通过 `sendMessage` 链路自动统计，前端不需要单独埋点接口。

### 两态布局

- 「更多 &gt;」：灰底 `#f5f5f7`、无边框、11px

**展开态**（`.ai_preset_expanded`）：
- 白底 + `border: 1px solid #e4e9f1` + `border-radius: 8px`
- `box-shadow: 0 4px 16px rgba(0,0,0,0.08)`
- 固定 `height: 252px`
- 内容：标题「更多常见问题」（14px/600）+ 右上 `×`（带独立灰底圆角容器）+ 两列固定网格
- 网格内容超出滚动，自定义 4px 细滚动条

### 两行测量算法（保证严格 ≤ 2 行）

```ts
async function doMeasure() {
  visibleCount.value = list.value.length
  await nextTick()

  const items = container.querySelectorAll<HTMLElement>('[data-ai-item]')
  const rowTops = new Set<number>()
  let firstThirdRowIdx = -1
  for (let i = 0; i < items.length; i++) {
    rowTops.add(items[i].offsetTop)
    if (rowTops.size > 2) { firstThirdRowIdx = i; break }
  }
  if (firstThirdRowIdx === -1) return  // 全部塞得下，不显示「更多 >」

  visibleCount.value = firstThirdRowIdx
  await nextTick()

  // 「更多 >」按钮进来后可能自身撑到第 3 行，往前踢
  while (visibleCount.value > 0) {
    const all = container.querySelectorAll<HTMLElement>('[data-ai-item]')
    const tops = new Set(Array.from(all).map(el => el.offsetTop))
    if (tops.size <= 2) break
    visibleCount.value--
    await nextTick()
  }
}
```

- 用 `[data-ai-item]` 选择器同时匹配普通问题按钮和「更多 &gt;」按钮，逻辑不需要区分。
- `measuring` 重入标志位 + `ResizeObserver` 只在宽度真正变化时触发，避免死循环。

### 关键决策

**为什么用 `[data-ai-item]` 而不是 class**：`measure()` 需要同时抓 PresetBtn（业务按钮）和「更多 &gt;」（原生 button），用 `data-ai-item` 标记语义更清晰、不与样式类耦合。

**为什么默认态背景是白色而不是透明**：截图确认默认态需要背景色遮住下方的消息，否则消息透过卡片可见，视觉上会出现两层叠加。

**为什么展开态浮层化**：展开态 252px 高度硬编码，若走 flex 文档流会把消息区压死（`globalChatDialog` 只有 480px 总高，扣掉标题 tabs 后基本没空间）。浮层化让消息区几何高度保持不变。

**为什么默认态保留在下方（点更多时不隐藏）**：展开态覆盖面积大、能完全遮挡默认态；保留默认态减少状态计算、避免关闭展开态时的显示闪烁。

**为什么切会话（vid/uid）时 reset closed 和 expanded**：这两个是纯 UI 状态，跨会话应该回到"首次进入"的初始态，不需要跨会话记忆。

### 被否决的替代方案

- ~~`el-popover` 承载展开态~~：popover 自带 arrow / padding / shadow，视觉不符；且位置切换会闪烁。
- ~~Vuex 存 `closed / list`~~：纯 UI 状态，不需要跨组件共享。
- ~~固定 108px 高度~~：单行内容时下半部空 48px，视觉污点；在最窄的 480px 容器里还会浪费显示空间。
- ~~`IntersectionObserver` 判溢出~~：只判"能不能看到"，判不了"在第几行"。

### 截断 tooltip 实现

```ts
function checkTruncation() {
  const el = textRef.value
  if (!el) return
  truncated.value = el.scrollWidth > el.clientWidth + 1
}
// mouseenter 时懒检测；文本变化时 nextTick 检测
```

- 只在 `truncated === true` 时 `el-tooltip` 才生效（`:disabled="!truncated"`），短文案不弹无意义 tooltip。
- 参考仓库先例 `tabsWorkBench/index.vue:29`。

### 关键决策

**为什么单独抽 `presetBtn.vue` 而不是直接在主组件里循环写按钮**：
- 之前把样式 class 从主组件层层传下来（`class="ai_preset_btn"` → `<el-tooltip>`），class fallthrough 落到 el-tooltip 的根元素而不是里面的 `<button>`，导致 `inline-flex / max-width` 等样式全部丢失，按钮各自独占一行。
- 把 pill 样式和 tooltip 逻辑封装在 self-contained 组件里，样式作用域清晰、不受父组件 class 传递影响。

**为什么 `data-ai-item` 挂在真正的 `<button>` 上**：`measure()` 需要读 `offsetTop`，必须选到布局参与元素；el-tooltip 的根元素是 wrapper，位置不代表按钮实际位置。

### 5.3 Script：状态 + 浮层定位 + 滚动补偿

```ts
// 新增状态
const aiOverlayRef = ref<HTMLElement | null>(null)
const aiCardVisible = ref(false)
const aiCardExpanded = ref(false)
const aiCardHeight = ref(0)
const opPanelH = ref(88)  // 操作面板实测高度
let opPanelRO: ResizeObserver | null = null

// 浮层定位：默认态贴工具栏，展开态离工具栏 10px + 左右各留 8px
const aiOverlayStyle = computed(() => {
  if (aiCardExpanded.value) {
    return { bottom: opPanelH.value + 10 + 'px', left: '8px', right: '8px' }
  }
  return { bottom: opPanelH.value + 'px', left: '0', right: '0' }
})

// 消息区 padding：默认态给等于卡片高度的 padding；展开态不给（按需求，展开态不处理遮挡）
const scrollerPadBottom = computed(() => {
  if (!aiCardVisible.value || aiCardExpanded.value) return 0
  return aiCardHeight.value
})

// 浮动按钮避让：默认态卡片显示时抬起
const floatBtnBottom = computed(() => {
  const base = 94
  if (!aiCardVisible.value || aiCardExpanded.value) return base
  return base + aiCardHeight.value
})

// 点击预设问题：走 operationPanel 暴露的 sendMessage
function onPresetSelect(text: string) {
  const panel = operationPanelRef.value
  if (typeof panel?.sendMessage === 'function') {
    panel.sendMessage(MESSAGE_TYPE.TEXT, text)
  }
}

// 卡片可见性变化时读高度 + 主动 measure + 贴底
function onAiVisibilityChange(payload: { visible: boolean; expanded: boolean }) {
  const wasAtBottom = useScrollReturn.arrivedState.bottom  // 读 resize 前状态
  aiCardVisible.value = payload.visible
  aiCardExpanded.value = payload.expanded
  nextTick(() => {
    const cardEl = aiOverlayRef.value?.firstElementChild as HTMLElement | null
    aiCardHeight.value = cardEl?.offsetHeight ?? 0
    useScrollReturn.measure?.()  // 手动更新 arrivedState（resize 不会自动触发）
    if (wasAtBottom) scrollToLastMsg()
  })
}

// onMounted 里挂 operationPanel ResizeObserver
const panelEl = operationPanelRef.value?.$el as HTMLElement | undefined
if (panelEl) {
  opPanelH.value = panelEl.offsetHeight || 88
  opPanelRO = new ResizeObserver(() => {
    const h = panelEl.offsetHeight
    if (h > 0) opPanelH.value = h
  })
  opPanelRO.observe(panelEl)
}

// onBeforeUnmount 里释放
opPanelRO?.disconnect()
opPanelRO = null
```

### 为什么在 chatDetail 做，不是 operationPanel

之前把卡片放在 `operationPanel` 里发现两个致命问题：
1. 卡片是 flex 文档流子元素，会挤压消息区，触发 `scrollTop` 漂移导致底部消息"被遮挡"（实为滚出可视区）。
2. `.chat_operation_panel { overflow: hidden }`，卡片无法用 `position: absolute; bottom: 100%` 溢出到面板之外。

搬到 `chatDetail` 后：
- 卡片是 `.chat_detail_comp`（`position: relative`）的绝对定位子元素，天然浮在消息区上。
- 消息区几何高度不再受面板变化影响。
- 只在需要的时候用 `paddingBottom` 给消息区留白避让默认态卡片；展开态直接盖住底部消息（用户主动打开、语义合理）。

### 为什么修 `bottom: 94px` 硬编码

`.has_new_message` 和 `.scroll_to_bottom_btn` 原本硬编码 `bottom: 94px`（对应操作面板旧高度 88 + 6 视觉间距）。默认态卡片让面板"逻辑高度"变大，这两个悬浮按钮如果保持 94px 就会落进卡片区域。改成 `floatBtnBottom = 94 + 卡片高度`，视觉正确。

### 为什么用 ResizeObserver 而不是固定值 88

- 操作面板高度并非完全固定：不同 tab（`chatType === PUBLIC` 有礼物开关）、不同断点下可能不同。
- 用 `ResizeObserver` 拿真实高度，避免以后面板高度变化时又要回来改硬编码。
- 大部分情况下 `opPanelH` 只在 mount 时读一次，之后不再变；开销可忽略。

### 为什么必须先读 `arrivedState.bottom` 再改 padding

`useScroll` 的 `arrivedState` 只在 scroll 事件里更新，不监听 resize。padding 变化不触发 scroll，所以 `arrivedState.bottom` 保留的是 resize **之前**的值 —— 正好是我们要的"用户原本是否贴底"的判据。之后再手动 `measure()` 强制刷新，用于后续逻辑。
